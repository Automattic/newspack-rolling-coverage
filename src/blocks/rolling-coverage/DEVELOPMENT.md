# Rolling Coverage block: development notes

The Rolling Coverage block (`newspack-rolling-coverage/rolling-coverage`) shows a coverage's entries on any page, polls for new ones, and loads older ones on scroll or with a Load More button. Editor code lives in `src/blocks/rolling-coverage/`. Server rendering and the entries REST routes live in `includes/blocks/class-rolling-coverage-block.php`, shared layouts in `includes/blocks/class-layout.php`, and the block bindings in `includes/blocks/class-entry-bindings.php`.

For how publishers use the block, see `README.md` in this directory.

## Attributes: block or layout

Settings for one placement are block attributes (`block.json`): coverage, polling, paging, ads, the ended notice, the cap (`latestOnly`, `latestCount`, `allUpdatesLink`, `allUpdatesLinkText`), `hideWhenEnded`, the author's name and avatar (`showAuthor`, `showAvatar`, both true by default; see Bylines below) and `layoutId`. `entriesPerPage` and `latestCount` are capped at `Rolling_Coverage_Block::PER_PAGE_MAX` (100). `align` and `anchor` come from block supports.

What the feed looks like is the layout: the block's inner blocks. That covers the Feed group with its layout and gap, the coverage-level blocks, and the entry template. A synced block (`layoutId > 0`) stores no inner blocks of its own. A block with `layoutId: 0` and inner blocks has a local, detached layout.

Built-in layouts also carry `latest`, `hidesWhenEnded`, `align` and `hidesAvatar`. These are not stored in the pattern. Picking a layout copies them onto the block's `latestOnly`, `latestCount`, `hideWhenEnded`, `align` and `showAvatar` through `layoutCapAttributes()` and `switchLayoutAttributes()` in `layouts.ts`: Rail, Clock, Margin and Split carry `hidesAvatar`, so picking one sets `showAvatar` to false. Switching layouts clears values the replaced built-in layout set and keeps values set by hand, so switching from one of those to a built-in layout without `hidesAvatar` sets `showAvatar` back to true, while switching between layouts without it keeps an Author avatar setting chosen by hand. Custom layouts leave `showAvatar` as it is, and no layout sets `showAuthor`.

## Layouts

A layout is a `wp_block` synced pattern whose content is one Rolling Coverage block. That block's inner blocks are the layout; its own attributes are ignored.

- **Injection.** `Layout::inject_layout()` runs on `render_block_data`. For a block with `layoutId > 0`, it swaps in the pattern's inner blocks (`Layout::get_layout_blocks()`) before core builds the block, so every reader of the inner blocks sees the shared layout. Only published patterns resolve. A block without a layout of its own, one with no inner blocks or whose pattern is missing, unpublished or holds no Rolling Coverage block, gets the Bulletin layout instead (`Rolling_Coverage_Block::default_layout_blocks()`), Feed group and Full Story Entry included, so it renders exactly as a block synced to Bulletin. That markup lives in `includes/blocks/bulletin-layout.html`: the editor's serialization of `innerTemplate()` with the outer Rolling Coverage block removed, and `{{share}}`, `{{pinned}}`, `{{full_story}}` and `{{read_more}}` in place of the words PHP translates. Its times take the site's time format when it loads. A change to Bulletin's template in `template.ts` needs the file regenerated: serialize the template in the editor (or copy a freshly created Bulletin pattern's inner markup) and put the placeholders back.
- **Nested blocks.** `Layout::detach_nested_blocks()` drops `layoutId` from every Rolling Coverage block nested inside a layout, and inside a detached block. Without it, a synced block inside a layout would pull the layout into itself at every level. The editor does the same with `detachNestedBlocks()` in `edit.tsx`.
- **Built-in slugs.** `Layout::BUILT_IN_SLUGS` lists them. A built-in's pattern does not exist until someone first picks it.
- **Create on pick.** The picker (`components/layout-picker-modal.tsx`) calls `createLayout()` in `utils.ts`. That serializes the layout's template and sends it to `POST rolling-coverage/v1/layouts/{slug}`. The editor supplies the markup because its template is what core validates the pattern's blocks against. `Layout::create_layout()` returns the existing pattern when one resolves (200). Otherwise it inserts a published pattern (201) titled by `Layout::get_title()`, sets its `_rolling_coverage_layout` post meta to the slug, files it under the `rolling-coverage` term of `wp_pattern_category` (created on first use), and stores the ID in the `rolling_coverage_{slug}_layout_id` option. The route needs permission to create and publish `wp_block` posts (`can_create_layout()`). A lock row in the options table (`acquire_lock()`, 30-second timeout) stops two first requests from creating two patterns. If the request fails, the picker inserts the template as a detached layout instead.
- **Reveal when ready.** The picker mounts as soon as it opens but stays hidden (`is-awaiting-previews`: `visibility: hidden`, so the previews still lay out and measure) until every card's preview has settled: its block has rendered and its height has held for three frames (`useSettledPreview()`). It opens anyway 3 seconds after the layouts load, or 10 seconds after opening if they haven't, so a slow request or preview can't keep it closed. Once open it stays open, and the previews stop being watched. While it's hidden, the Choose and Change Layout buttons show as busy, "Loading layouts…" is announced, and Escape closes it; the buttons claim Escape first so the editor canvas doesn't move focus off them. When it opens, focus goes to the current layout's card, else the first card, else the dialog when the layouts are still loading. If focus has moved elsewhere by then, the picker closes instead of taking it back. The frame's open animation is held until it's revealed.
- **Lookup.** `Layout::get_layout_id()` reads the option and falls back to the oldest published pattern tagged with the slug, then repairs the option. This covers a persistent object cache that loses the option.
- **Inserted from Patterns.** The inserter adds a layout as a `core/block` reference, and core locks the blocks inside a synced reference, so the coverage couldn't be picked. `pattern-insertion.tsx` replaces a reference to a layout with a Rolling Coverage block whose `layoutId` is the pattern, plus `switchLayoutAttributes()` for a built-in layout, as the picker does. A layout here is a built-in, or a pattern in the layout category that passes `isLayoutContent()` in `utils.ts`: its only top-level block is a Rolling Coverage block with no coverage. The picker lists custom layouts by the same test; anything else stays a pattern. It also converts a layout reference already in a story when the story opens. It skips the `wp_block` editor and any reference it can't replace, and keeps the replacement out of undo history, so undo never lands on the locked reference.
- **Edit Layout.** The toolbar button links to `getLayoutEditUrl( layoutId )` in `utils.ts`, which carries only the pattern's ID. A layout pattern being edited (`isLayoutPattern` in `edit.tsx`) always previews the sample entries in `samples.ts`, never a story's coverage, so the Pinned Entry, Entry and Full Story Entry all show. A detached layout in a story previews the story's entries instead.
- **Editor config.** The editor gets the built-in pattern IDs and the category ID from `Rolling_Coverage_Block::localize_block_config()`; `utils.ts` keeps them in `layoutIds` and `layoutCategoryId` and updates them when `createLayout()` succeeds.

## Template structure contract

The server finds the parts of a layout by class name and binding, not by position. Each class in `template.ts` mirrors a PHP constant; change both together.

- **Feed group.** A `core/group` with the class `newspack-rolling-coverage-feed` (`Rolling_Coverage_Block::FEED_CLASS`). It may sit at the top level or inside plain groups (`feed_path()`). Its Block spacing becomes `--newspack-rolling-coverage-gap`, and its layout (flex or grid) decides how entries are placed. A layout without one uses its top-level blocks as the items.
- **Entry groups.** Groups at the Feed's top level with the class `newspack-rolling-coverage-pinned-card` (`PINNED_CARD_CLASS`), `newspack-rolling-coverage-regular-entry` (`REGULAR_ENTRY_CLASS`) or `newspack-rolling-coverage-breakout-entry` (`BREAKOUT_ENTRY_CLASS`, the Full Story Entry). Each full layout has all three, named Pinned Entry, Entry and Full Story Entry in List View and locked in place. An entry renders through exactly one of them (`for_entry_kind()`). An entry whose breakout post is published renders the Full Story Entry alone when it's unpinned, or when it's pinned and the group holds the pinned row (`is_full_story()`: the template holds the group at the top level, `Breakout::get_published_breakout_url()` is not null, and the entry isn't pinned or `full_story_takes_pinned()` finds a top-level Full Story Entry holding the pinned row at any depth, `Entry_Bindings::has_pinned_row()`). Any other pinned entry renders the pinned card alone, and every other entry the regular group alone, with the Full Story Entry dropped. A capped feed shows every entry as unpinned, so it never needs the pinned row. The pinned row inside the group renders only for a pinned entry (`Entry_Bindings::filter_pinned_group()`). In the built-in layouts, the Full Story Entry holds the pinned row in Bulletin, Stream, Minute, Rail, Clock, Margin, Byline and Split; Wire, Digest and Flash show a pinned entry as the pinned card whatever its breakout post. A pinned Full Story entry keeps `data-pinned` on its article, so the view script keeps it with the pinned entries, but nothing that shapes the pinned card touches it: it keeps its group's closing separator unless it's the last entry, as an unpinned one does, never sticks as a card, and the stored layout styles count the pinned card as unshown when only such entries are pinned. The editor mirrors the rule with `fullStoryTakesPinned()` (`template.ts`) and `isFullStoryContext( context, takesPinned )` (`layout.ts`). A template missing the pinned or the regular group is used as it is for every entry; a template without a Full Story Entry shows an entry with a published breakout post as a normal entry, pinned or not, and a Read more bound to the post still links to it. The Full Story Entry takes part everywhere the entry group does: `is_entry_group()`, the closing separator (`without_closing_separator()`, `withoutClosingSeparator()`, and `SEPARATOR_PARENTS` and `CLOSING_SEPARATOR` in `view.ts`), layout styles (`store_entry_layout_styles()`, `entry_layout_class()`), grid placement and column rules (below).
- **Grid placement and column rules.** In a grid Feed (Split), `template_grid_placements()` returns a `breakout` placement next to `card` and `entry`: a Full Story article takes the group's own placement, else the entry group's, and `without_grid_placements()` strips it with the other entry groups. The pinned card's placement goes to the first pinned entry shown as the card, so a pinned Full Story entry never takes it (`first_pinned_entry_id()` skips pinned entries with a published breakout post where the group takes them, and the editor's `leadPinContext` does the same). Like the stylesheet, which lets the entries beside the card take the full row while no pinned card shows (`:has(.newspack-rolling-coverage-pinned-card)`), the editor counts only an entry shown as the card (`showsPin`), so a feed whose only pinned entries are Full Story entries leaves no empty column beside them. An entry that heads its column also gets a top border on the group (`with_top_border()`), `column_rules()` returns a `breakout` declaration, and `render_block()` prints it as `data-breakout-rule` on the wrapper, so `view.ts` (`placeColumnRule()`) can give a Full Story article that is demoted from the head of its column back its own rule. Split's group carries the same placement as its entry group.
- **Layouts without entries.** A layout whose Feed holds only coverage-level items, like Alert, has an empty entry template. `render_block()` renders no entries for it, Lite Site pages included, no "no entries" message and no way to load older entries, and marks the wrapper `data-entries="none"`. The view script still polls, so the status and When ended keep working, but adds no entries from a poll and never reloads for a `staleTemplate` reply (see Server rendering and polling), since it has no entries to show. `style.scss` hides an entries container that holds nothing but empty items. In the editor, Show and Number of entries are hidden for such a layout while Show is Latest, as Ticker does for Show, since the coverage-level link renders only in a capped feed and All would make the story a coverage page; the "No published entries yet" notice is skipped too.
- **Header and footer.** `Rolling_Coverage_Block::layout_parts()` splits the Feed's items. Coverage-level items render once: the ones before the first per-entry item form the header, the ones after it the footer. Everything else is the entry template. `Entry_Bindings::is_coverage_item()` decides what is coverage-level: the Follow Coverage, Check for Updates, Coverage Status and Update Timer blocks, a heading bound to `coverageName`, the all-updates paragraph, or any block holding one of these. The entry groups are never coverage-level. The editor mirror is `layoutParts()` in `template.ts`.
- **All-updates paragraph.** A `core/paragraph` with the class `newspack-rolling-coverage-all-updates` (`Entry_Bindings::ALL_UPDATES_CLASS`). It links to the coverage page. It renders only in a capped feed with `allUpdatesLink` on, and drops on the coverage page itself (`render_block()`, `is_coverage_page()`). Detection uses the class, never the text. The text a new layout starts with is `See all %s`, filled in `allUpdatesLink()` (`template.ts`) with `ENTRY_PLURAL`, the `entryPlural` editor config key (`Entry_Name::word( 2 )`, empty when the site sets no name, which gives the translated `See all entries`). It is stored as the paragraph's content, so an editor's own wording is kept, and a stored layout keeps the text it was created with until its pattern is trashed and the layout picked again. A block on a shared layout (`layoutId` set) can replace the text with its own `allUpdatesLinkText`: trimmed, escaped and swapped in for the paragraph's whole content in `Entry_Bindings::link_all_updates()` (`Rolling_Coverage_Block::get_all_updates_link_text()`, set while the coverage-level blocks render), so the layout's formatting inside the paragraph gives way to plain text. Empty keeps the layout's text, and a detached layout ignores it, as its paragraph is edited in place. The editor mirrors it with `withAllUpdatesText()` (`template.ts`) in the shared layout's preview, shows the layout's own text (`allUpdatesTextOf()`) as the field's placeholder, and on Detach writes the text into the copied paragraph and clears the attribute; switching to an editable built-in layout clears it too, while switching to another shared layout keeps it. The field waits for the shared layout to load, so it never shows the default layout's text.
- **Bylines.** Post Author Name and Avatar blocks in an entry follow the block's `showAuthor` and `showAvatar` attributes, the site's Avatar Display and the entry's author. All of it applies to the template, not the rendered blocks, so a group the removed blocks leave empty goes too: the built-in layouts give the avatar and name a flex group of their own, which would otherwise still take a Block spacing gap in its row. `without_author_blocks()` does the removal; it drops a group that held only removed blocks and keeps one that was empty in the layout.
  - `with_author_settings()` applies the attributes in `render_block()`, before `persist_block_config()` stores the template, so polls, load more and the jump to the latest entries render the same way. The two work apart: `showAuthor` false drops the name, and `showAvatar` false drops the avatar along with any column that held only an avatar.
  - `with_avatar_display()` drops avatars and their columns when avatars are off. Its result is the same for every entry, so `render_block()` and `get_entries()` apply it once per request, after the template is stored, which keeps the stored config independent of the setting.
  - `render_entry()` drops the name and avatar, but not the avatar's column, for an entry the Slack bot wrote (`is_bot_authored()`), so Byline's text lines up with the other entries. It skips the author lookup when the shaped template holds neither block, and `render_block()` and `get_entries()` prime the author caches for each page of entries (`prime_author_caches()`), as the entries preview route does, except for a lite page or a template with neither block, where nothing reads the author.
  - `hide_slack_bot_byline()` stays as a render-level safety net for the bot's author blocks that reach an entry outside its template, such as in its own content. `size_entry_avatar()` writes an avatar's block size as inline width and height, and drops the empty wrapper core prints for one with avatars off.
  - The editor mirrors this in `template.ts`: `withAuthorSettings()`, `withoutAvatarColumns()` and `withoutByline()` shape the previews in `useLayoutPreview()` (`layout.ts`) for sample entries, real ones, the Slack bot's (flagged `hidesByline` by the entries preview route) and a shared layout, and an editable layout hides the blocks they leave out (`hiddenAuthorBlockIds()`), avatars included when Avatar Display is off.
  - "Author name" shows when the entry template holds a Post Author Name block, and "Author avatar" when it holds an Avatar block and the site's Avatar Display is on (`SHOW_AVATARS` in `config.ts`), whatever the other is set to.
  - Stream heads each entry with a Byline group of the avatar and an Author + Date group holding the name and relative date. On the pinned card a Meta row (`streamMetaRow()`, flex, `space-between`) holds the Byline and, at its far end, the pinned row for screen readers only (`streamPin()`: `pinnedRow( { icon: false, hidden: true } )`), so a pinned Stream entry shows no pin. Bulletin's pinned row keeps its pin visible and sets only the label for screen readers (`pinnedRow( { iconOnly: true } )`, `screen-reader-text` on the paragraph), at the far end of the Meta row on the pinned card and in its Full Story Entry, where it takes `READABLE_ACCENT`. The name uses the header font and the date the body font, which put their baselines a pixel apart, so the group carries `newspack-rolling-coverage-byline-text` (`BYLINE_TEXT_CLASS`), and `style.scss` aligns its children on the baseline; Byline's Author + Date group does the same. Block settings have no baseline option. In Rail, Clock and Split the links row below the content holds the Author group (avatar and name) and Share, in Split's pinned summary too. Margin stacks the Author group above Share in its side column. Byline keeps the avatar in a column of its own beside the name and date.
- **Context.** Coverage-level blocks render with `newspack-rolling-coverage/coverageId` and `newspack-rolling-coverage/coverageStatus` in context (`render_coverage_blocks()`). Each entry renders with its own `postId` and `postType` (`render_entry()`).

## Share and Read more

In the built-in layouts, each entry has a "Share" link to the entry (`shareLink()` in `template.ts`). No entry group has a "Read more" link to the breakout post, since the Full Story Entry's card stands in for it (see Breakout cards); Bulletin's Full Story Entry has a Read More button bound to `breakoutUrl`, and a template of a site's own can hold either. Both are core paragraphs the server finds by class, and both render nothing when there is nothing to link to. A Read more button bound to the entry's breakout post works the same way, as described below.

- **Read more** carries `newspack-rolling-coverage-read-more` (`Entry_Bindings::READ_MORE_CLASS`). `Entry_Bindings::link_read_more()` links it to the entry's published breakout post (`Breakout::get_published_breakout_url()`) and drops it when there is none. A Buttons block the missing link leaves empty goes too (`Rolling_Coverage_Block::drop_empty_entry_buttons()`), and so does any block it leaves empty inside the pinned card (`without_breakout_link()`). The editor preview mirrors both.
- **Share** carries `newspack-rolling-coverage-share` (`Entry_Bindings::SHARE_CLASS`). `Entry_Bindings::link_share()` links it to the entry's share URL (`Social_Sharing::get_entry_share_url()`: the entry's permalink, with the page it was shared from in `rc_source`), marks it `data-rc-share` with `role="button"`, and gives it an accessible name that includes the entry, such as "Share: Polls close at 8pm". It drops when the entry isn't published.

`Entry_Bindings::link_paragraph()` puts the link on the template's placeholder link (`href="#"`), or wraps the paragraph's content in a new one. A link the author added inside the paragraph is left alone, since links can't nest.

A `core/button` bound to the `newspack-rolling-coverage/entry` source with the key `breakoutUrl` or `shareUrl` works the same way (see the entry bindings above). A share button renders as the link icon alone (`Entry_Bindings::show_share_icon()`), and `share-preview.tsx` marks it in the editor so `editor.scss` previews it the same way.

The Share block's view script, `src/blocks/share/view.ts`, handles the clicks. `render_block()` enqueues it with every feed, and it listens on each feed present at load for `[data-rc-share]` and the Share block's button: it opens the device's share sheet where there is one, and otherwise copies the link and says "Link copied." in a Newspack UI snackbar, or without Newspack UI in the status region of the button's feed. Since a feed can sit inside another feed's entry, a tap reaches every feed around the button, and only the closest feed with listeners handles it. A feed added after load has no listeners, so the closest feed around it that was there at load handles its buttons, and announces in its own region when the button's feed is capped. Like `ownElement()` in the feed's view script, its lookups skip a nested feed's elements, so the shared title never comes from a nested feed's entry.

### The Share and Breakout Post Link blocks

`newspack-rolling-coverage/share` and `newspack-rolling-coverage/breakout-post-link` are the earlier blocks for these links. They are hidden from the inserter (`supports.inserter` is false) and no built-in layout uses them, but they stay registered and allowed in the entry template (`ENTRY_ALLOWED_BLOCKS` in `template.ts`), so layouts and entries that hold them keep rendering. The server and the editor count the Breakout Post Link block as the Read more link (`is_breakout_link()`, `isBreakoutLink()`).

- **Share.** Editor code in `src/blocks/share/`, server rendering in `Share_Block` (`includes/blocks/class-share-block.php`). It renders a `<button>` with the entry's share URL in `data-share-url` and its `label` attribute as its text ("Share" by default), or nothing when the entry has no share URL. Its `aria-label` uses the site's entry name ("Share this update"), or "Share this entry".
- **Breakout Post Link.** Editor code in `src/blocks/breakout-post-link/`, server rendering in `Breakout_Post_Link_Block` (`includes/blocks/class-breakout-post-link-block.php`). It renders a "Read More" link to the entry's published breakout post, or nothing until there is one. It has no attributes, so its text can't be changed.

## Breakout cards

Once an entry's breakout post is published (`Breakout::get_published_breakout_url()`), feeds point readers to it. A layout with a Full Story Entry shows the post as a card, built from core blocks, in place of the entry's text. A compact layout, with no Post Content, shows the post through its own entry template, as the post's title and summary. A layout with neither shows the entry as usual. The code is in `Breakout_Card` (`includes/blocks/class-breakout-card.php`) and `Rolling_Coverage_Block::render_entry()`.

- **The card data.** `Breakout_Card::for_entry()` reads the post's link, its title (core's `the_title` filter, without the "Protected:" prefix `get_the_title()` adds) and its summary, both as plain text and escaped where they are printed. `for_entry()` also returns the post's featured image ID (`image_id`). `Rolling_Coverage_Block::render_entry()` asks for the summary only when it shows: when the part of the template the entry renders through holds a Post Excerpt, and before the entry renders. A feed loads its entries' breakout posts with their meta and terms, then those posts' featured images, a query each (`Rolling_Coverage_Block::prime_breakout_posts()`), so the cards' own lookups add no queries per entry. Newspack's content gate reads a post's terms uncached (`wp_get_post_terms()`) when it summarizes a post without an excerpt, which the hour-long summary cache bounds.
- **The summary.** It is the same for every reader, since it's cached and polls render it for everyone, so nothing in it is rendered for the reader who happens to load the page first.
  - A password-protected post (non-empty `post_password`) gets none.
  - A post with a hand-written `post_excerpt` gets that excerpt, restricted or not.
  - A restricted post without one gets its Newspack content gate's free preview (`Content_Gate::get_teaser_outside_article()`, built for a signed-out reader), else none. `teaser_summary()` drops the ` [&hellip;]` Newspack's overlay gate ends the preview with and cuts it to the `excerpt_length` filter's length (`Post_Type::get_html_excerpt()`), ending it in an ellipsis when it was cut or carried that marker. Newspack gives no teaser while WooCommerce Memberships is active, so a Memberships rule or another restriction leaves no summary. Restricted means `Entry_Bindings::is_withheld()` (a Newspack content gate outside the post's page, judged by `Content_Gate::get_teaser_outside_article()`, or a WooCommerce Memberships rule) or a `newspack_post_has_restrictions` callback, which is also the same for every reader.
  - Any other post gets its opening words from `Entry_Bindings::public_summary()`: its stored blocks read without rendering them, after `public_content()` removes the blocks Newspack hides from readers who aren't signed in, cut to the `excerpt_length` filter's length (core's translatable 55 by default) and ended with an ellipsis when cut. Core's generated excerpt would render the post's blocks, which Newspack's `Block_Visibility::filter_render_block()` shows or hides for the current reader, so a subscriber's render would put members-only text in everyone's summary. It is cached in the object cache (group `newspack_rolling_coverage_breakout_card`) by post ID, `post_modified_gmt` and the excerpt length, so an edit makes a new key and a context asking for another length gets its own. Which blocks Newspack hides also depends on its gates and Reader Activation, which can change without an edit, so each summary expires after an hour.
  - A post whose summary leads back to itself, such as through a feed in its free preview, gets no summary there.
  - When the post gives no summary (password protected, a gate with no free preview, another restriction, or no words anyone may read), `summary_or_entry_words()` uses the entry's own opening words (`Entry_Bindings::public_summary()` at the excerpt length), which readers could already see in the feed, so a card never leaves a layout's text column empty. A restricted entry gives none, and the card shows its title alone.
  - The summary is worked out before the entry's own render starts, so neither the card's filters nor that entry's are active while a free preview builds.
- **The Full Story Entry.** A `core/group` at the Feed's top level, built only from core blocks and the plugin's bindings, so publishers edit it in the editor like the rest of the layout. It holds one group, the "Card" (`newspack-rolling-coverage-breakout-box`, `Breakout_Card::BOX_CLASS`, `BREAKOUT_BOX_CLASS` in `template.ts`), whose styling is block settings (see the styling policy). Inside it the built-in layouts put:
  - the Full Story Label: a `core/paragraph` named "Full Story Label" whose content is bound to the `newspack-rolling-coverage/entry` source with the key `breakoutLabel` (`fullStoryLabel()`), small, bold, in `READABLE_ACCENT`, with the header font;
  - Post Featured Image (`fullStoryImage()`), Post Title and Post Excerpt (`excerptLength` 25, no more text);
  - the entry's own Post Date, Post Author Name, avatar and Share, which are the entry's and not the post's.
- **Per-layout designs** (`template.ts`; `fullStoryGroup()` and `fullStoryBox()` build the group and box, and the row templates take `kind: 'pinned' | 'entry' | 'fullStory'`). Bulletin: a box with no border on `PINNED_BACKGROUND` (`fullStoryBox()` with `outlined: false`), so hovering doesn't change it, padded `var:preset|spacing|50` like the pinned card (`CARD_PADDING`), with the same gap between its columns; a Meta row of the pinned row (`pinnedRow( { iconOnly: true, color: READABLE_ACCENT } )`, which renders only for a pinned entry and makes the group take pinned entries), the label, time and Share, then a `core/columns` block with a column of the title (`large`, like the entries' titles and the pinned card's) and excerpt (at the entry text's size and color, `fullStoryExcerpt( slugs, { asEntries: true } )`; small, in the entry text's color, in Byline and Split) and a Read More button (`fullStoryReadMore()`, a core Button bound to `breakoutUrl`, in `ACCENT` with `ACCENT_CONTRAST` text like the pinned card), then an 11rem image column (`aspectRatio` 4/3, `scale` cover, `medium_large`). Like the pinned card, the group has no closing separator, so the Feed's gap alone sits below it. Stream: a Meta row (`streamMetaRow()`, flex, wrapping, `space-between`) of the Byline group and, at its far end, a Marks group of the screen-reader-only pinned row (`streamPin()`, which renders only for a pinned entry and makes the group take pinned entries), the label and `fullStoryArrow()`, which drops below the byline at the row's start when the row wraps; the image, with a `var:preset|spacing|30` margin above and below (`fullStoryImage( { margin } )`); the title (`large`); the excerpt at the entry text's color and size (`fullStoryExcerpt( slugs, { asEntries: true, fontSize } )`, `themeFontSize( sizes, 'medium', 'normal' )` like Stream's Post Content); and a row holding Share. Rail, Clock, Margin, Byline and Split: the label, the title, the image and the excerpt in the layout's content column (`columnFullStoryBox()`, except Rail and Margin, below); Rail and Clock pass their links row (author and Share) as the box's footer, so it sits inside the card in a Footer row (`fullStoryFooter()`: flex, `space-between`, with `fullStoryArrow()` at its far end), and Clock sets the excerpt small in the entry text's color (`columnFullStoryBox()`'s `asEntries` and `excerptSize`) and gives the image a `var:preset|spacing|20` margin above and below (`imageMargin`) and the box the `RADIUS_MEDIUM` corners (`boxRadius`), while the others keep the date, author and Share where the layout places them for an entry. ## Excerpts, untitled and media-only entries

Every layout that summarizes an entry reads the same words: the stored HTML of its blocks without their media blocks, at any depth (`Entry_Bindings::words_html()`), read without rendering it, since rendering could recurse through an embedded Rolling Coverage block. Media blocks are the ones `media_kind()` names: images, galleries, videos, audio, covers showing an image or a video, and embeds, which are a photo or video by their oEmbed `type`, or a video or audio by `providerNameSlug` (`VIDEO_EMBED_PROVIDERS`, `AUDIO_EMBED_PROVIDERS`). So a caption, the text over a cover and the URL stored inside an embed block never count as words, while a list, a heading, a quote or a code block does, which core's `excerpt_remove_blocks()` would drop (it skips a List whose items are List Item blocks, and no filter reaches that check). Two more kinds of block add nothing (`is_wordless()`): a block hidden with the editor's Hide block (`metadata.blockVisibility` false, which core renders nowhere), and the controls in `CONTROL_BLOCKS` (buttons, a file's download link, social links, search, navigation), whose text is a label. A synced pattern stops an entry getting a media title, since its text isn't stored in the entry, though it adds nothing to the excerpt; other dynamic blocks, such as a poll, don't count at all, so a photo beside one still gets a media title. Everything is read after Newspack's `Block_Visibility::strip_blocks_hidden_from_public()` (when Newspack is active) removes blocks meant for members (`Entry_Bindings::public_content()`), so no summary shows members-only text or media to everyone.

- **Excerpt.** `Entry_Bindings::entry_excerpt()` on `get_the_excerpt` (priority 11, after core's `wp_trim_excerpt()`) replaces core's generated excerpt for an entry with no hand-written excerpt: the entry's words cut to the `excerpt_length` filter's value (core's translatable 55 by default) and ended with `excerpt_more` when cut (`Post_Type::get_html_excerpt()`), escaped like core's. It reaches core's Post Excerpt block on the site, which asks for 101 words and cuts the result to its own Max number of words, and the editor through `Post_Type::get_editor_excerpt()`, so the editor needs nothing of its own. Core's excerpt reads the content through `the_content`, which is where Newspack's content gate and WooCommerce Memberships restrict it, so an entry either one restricts (`is_withheld()`: `Content_Gate::get_teaser_outside_article()`, or a Memberships rule read by `is_restricted_by_membership_rule()`) keeps the excerpt the filters before this one built. An entry with neither words nor media still has an empty excerpt, and the editor's Post Excerpt says "No excerpt found" for it.
- **Title.** A Post Title carrying `newspack-rolling-coverage-entry-link` (`Entry_Bindings::ENTRY_LINK_CLASS`, used by Ticker) shows an untitled entry's fallback title through `Entry_Bindings::untitled_fallback_title()` on `the_title`. `get_fallback_title()` picks it: the hand-written excerpt, else the media title, else the opening words of the first block with words (`headline_html()`: a block with text of its own, or a list, taken whole; a wrapper such as a group is looked into; a block whose text ends with a colon reads on into the blocks after it, since it announces them), cut to `UNTITLED_FALLBACK_WORDS`, so a heading or an opening line stands alone rather than running into the text after it. A restricted entry (see below) has none. The editor gets it as `fallbackTitle` from the entries-preview route.
- **Media title.** An entry with no words outside its media, such as a lone photo, gets a media title from its first media block (`Entry_Bindings::get_media_title()`) as both its excerpt and its fallback title: the media's label, `Photo`, `Gallery`, `Video`, `Audio` or `Embed`, then the block's caption, the text over a cover, or an image's alt text (a gallery without a caption takes its first described image's), cut to `UNTITLED_FALLBACK_WORDS`. A media block without any of those is named by `media_name()`: an embed of a titled post on this site that readers can open (`url_to_post_id()`, which keeps `url_to_postid()`'s answer in the object cache for an hour, then `is_post_publicly_viewable()`) by that post's raw title, read without `the_title` so two untitled entries embedding each other can't loop through `untitled_fallback_title()`; any other embed with a URL as "Embed from" its host without `www.`; and the rest by their label.

Everything else that reads an entry's excerpt gets these words too, such as the REST API's `excerpt.rendered`, oEmbed cards and SEO plugins' descriptions. Other summaries of an entry don't use the media title. The ones everyone can see read only what everyone may read, and none of a restricted entry's text, its hand-written excerpt included. An entry is restricted when it's password protected, a Newspack content gate covers it, or a WooCommerce Memberships rule restricts it (`Entry_Bindings::is_restricted()`, through `is_withheld()`). The answer is the same for every reader, so it's safe to cache: the gate is judged for a signed-out reader, as Newspack judges a post listed outside its own article, and the Memberships rule is read from its rules and the posts an admin marked public, not through `wc_memberships_is_post_public`, which Newspack's newsletter-link access answers per reader.

- The Share link's accessible name and a breakout post's title use the title, else `Entry_Bindings::public_name()`: `public_summary()`, the opening words of `public_content()` outside its media, else the media title, so a lone photo is still told apart. A restricted entry gets nothing.
- Push notifications use the hand-written excerpt or `public_summary()`. A restricted entry is announced with "Read the latest update." in place of its words, under its title or the coverage name. An untitled entry with no hand-written excerpt and no words of its own, such as a lone photo or one whose text is all members-only, isn't announced, restricted or not.
- The `LiveBlogPosting` schema, cached for every visitor, builds each update from `public_content()` and leaves restricted entries out.

The entries list in the admin reads `Post_Type::get_entry_summary()`, which includes everything, as does the AI prompt, which editors send to the AI provider.

## Server rendering and polling

`Rolling_Coverage_Block::render_block()` queries the newest entries, renders each one through the entry template (`render_entry()`), adds an ad after every `adsInterval` entries when enabled (up to `Ads::INITIAL_AD_CAP`, 3, across the page and its loaded older entries: `Ads::is_capped_ad_position()` counts positions from the top, pinned entries included, and the load-more endpoint continues from `entry_offset`; polled entries add one every `adsInterval` new entries with no cap, carrying the count between polls in `polledCount`), and wraps the result in the Feed group (`render_feed()`). It hands the view script its state through `data-*` attributes on the wrapper.

Entries can arrive after the page loads, by poll or load more, holding blocks none of the first entries had. So `render_block()` enqueues up front the styles of the blocks entries commonly hold (buttons, separator, icon, image, gallery, which Slack's photos use, Coverage Status and Update Timer) and of every block in the template (`enqueue_template_block_styles()`), and the view scripts of Share, Coverage Status, Update Timer and, once OneSignal is configured, Follow Coverage. A Follow, Status or Update Timer block inside an entry, or in a feed nested in one, then works whenever it arrives.

The page, polls, load more and lite pages render each entry as a post in a loop of the feed's own (`setup_entry_postdata()`). Newspack's content gate serves a gated post's teaser, without the gate, only to a post set up in a loop, as it does in its own lists of posts. So on those paths an entry a gate covers (by post type, by category, or through a gate with only exclusion rules) renders as its teaser for every reader, including readers the gate lets through. The entries route's replies are public and cached, so they can't vary by reader. `tests/test-gated-entries.php` holds each path to the loop setup.

Where the gate stands aside for a whole request, loop or not, `withhold_gated_entry()` covers the rendered content. On `the_content` while an entry renders, it swaps a gated entry's content for the same teaser (`Content_Gate::get_teaser_outside_article()`). The gate stands aside on WooCommerce's account, cart and checkout pages, which a feed placed site-wide renders on, and in syndication feeds, which it leaves to its feed setting. That setting judges each feed item, the host post rather than its entries, so in a feed the swap follows it: none when `Content_Gate_Advanced_Settings::get_feed_restriction_mode()` answers `off`, and the teaser for `truncate` and `exclude`, since a feed set to remove restricted articles keeps the host post unless a gate covers it too. Everywhere else the swap hands back the teaser the gate already put in place. It runs at priority 999, where Newspack swaps a gated post's content, after the content filters, so the finished teaser isn't run through them again. It swaps the rendered content rather than `post_content` because core's Post Excerpt block reads the entry by ID. `tests/test-entry-teasers.php` covers the Post Content and Post Excerpt layouts on a page and in RSS, under each feed setting.

`render_block()` also stores the entry template, with the ad and cap settings, in an option named `rc_tpl_{coverage_id}_{hash}` (`persist_block_config()`), and prints the hash as `data-template-key`. REST requests render entries from that stored config (`load_block_config()`), so polled entries match the page.

- **Retention.** Each coverage keeps its 50 most recent configs (`CONFIGS_KEPT`, tracked in the `rolling_coverage_template_hashes` term meta). That is far more than one coverage shows at once across pages, widgets and capped feeds, so the configs in use stay stored while those of edited layouts age out. Rendering a stored config writes nothing, since every term meta write flushes the site's term query caches, except when it is next in line to drop: then it moves to the end of the list.
- **Stale keys.** A page cache (Batcache, or a publisher's CDN) can serve a page long after its config was dropped, or the option write can fail. A request whose `template_key` names no config stored for the coverage gets `staleTemplate: true` and no entries, rather than entries in the default template. A cursor poll gets it only when the coverage has changed since its cursor, whether by an edit, a new entry or a removal, keeping its cursor; one with no change answers as usual. A shared poll gets it whenever its key is unknown, while shared polling is on. The view script reloads on the reply, then waits `OVERFLOW_RELOAD_RETRY_MS` (the overflow window) before reloading again for the same page and key, so a tab that was served a stale cached copy recovers once the cache expires instead of failing its checks forever. Load more gets it with no-cache headers, so no cache keeps the reply once the page's reload stores the config again. A lite request is served as usual, since lite entries don't use the template, and so is one with an empty key, which renders the defaults.

REST routes, in the `rolling-coverage/v1` namespace (`register_routes()`):

- `GET /coverages/{id}/entries` is public. With `cursor`, it is a forward poll for new and edited entries, and for entries taken down since the cursor, which it names for the page to drop (`Post_Type::record_entry_unpublished()` records when an entry leaves `publish`). It finds them by modified date. Core's `wp_publish_post()`, which cron uses for scheduled entries, changes only the status, so `Post_Type::stamp_publish_modified_gmt()` moves an entry's modified date to the moment it goes out. `Post_Type::record_entry_published_gmt()` records that same second as the time the entry went out, which tells a new entry from an edit (`Poll_Cursor::is_new()`): reading the clock again could give the next second, and the entry's first edit would then arrive as another new entry on a page that already has it. With `before`, it returns the next page of older entries. With `recent`, it answers a shared poll (see Shared polling below); a request with none of the three gets a 400. `template_key` is required; a key the coverage doesn't store gets `staleTemplate` (see above). Capped feeds send `latest`, so their requests stay capped whatever config the key loads, including a lite page's request served without a stored config. Lite pages send `lite` (see Lite Site pages).
- `GET /coverages/{id}/entries-preview` needs `edit_posts`. It returns entry IDs for the editor's preview, each with a `breakout` object (see Breakout cards).
- `POST /layouts/{slug}`: see Layouts.

Polling, in `view.ts` (`initBlock()`, `poll()`):

- The block polls every `max( pollInterval, minPollInterval )` seconds. It polls only when the coverage was `active` at render time (`data-status`), so a paused or ended coverage never starts polling. Polling stops while the tab is hidden and resumes when it shows. It stops for good once a poll reports the coverage `archived`; after a `paused` poll it carries on, to follow the coverage if it resumes. A feed that saw the end shows a reopened coverage, or an edit to an entry it already shows, only after a reload; its shared-entry view loads the live feed's page rather than taking it in place (`canShowInPlace()`). Its notice comes from the Ended settings it loaded with and the breakout post the ending poll named, so a later change to either shows only after a reload too.
- A layout holding a Check for Updates block among its coverage-level blocks switches the feed to checking only on request: `Rolling_Coverage_Block::checks_on_request()`, `data-new-entries="button"`, and the view script's button handling. See `../check-updates/DEVELOPMENT.md`.
- A feed can sit inside another feed's entries, possibly for the same coverage. A feed acts only on its own elements: `ownElement()` and `ownElements()` in `view.ts` skip any element whose closest block wrapper is another feed, and every lookup of the sentinel, control, status and sticky cards goes through them; entry lookups stay on the block's own entries list. Use them for any new query inside the block, since a nested feed repeats the classes and entry IDs.
- A site-wide minimum comes from the `NEWSPACK_ROLLING_COVERAGE_MIN_POLL_INTERVAL` constant or the `newspack_rolling_coverage_min_poll_interval` filter (`get_min_poll_interval()`). Poll responses send `Cache-Control: public, max-age=N`, where N is the larger of `POLL_MAX_AGE` (5) and half the minimum (`poll_response()`), so readers polling at the same moment share a cached reply. Open pages learn a changed minimum from their next poll. The editor gets it as `minPollInterval` from `localize_block_config()` and shows it under Poll interval.
- **Shared polling.** Pages poll one URL every reader of the page shares (`pollUrl()`): `recent=1` in place of the cursor and the ad count, with `template_key`, `host_post_id` or a capped feed's `latest`, and `lite` on a lite page. The edge then keeps answering it right after a change, when each page's own cursor URL is new to it. `shared_poll_response()`, cached like a cursor poll, answers with the coverage's current cursor and every change since the window start (`since`), newest first: published entries, rendered, with when they were first published, and entries taken down, with when (`unpublished`). The window starts at the last save of a published entry from before a cutoff at least `max( SHARED_WINDOW, 4 × get_min_poll_interval() )` seconds back, rounded down to the minute so refreshes within a minute share the query (`shared_window_start()`), or takes in every change when no published entry is that old, so it always holds the last change before that cutoff, and a page that has that change can apply the reply however long the coverage has been quiet. `readSharedReply()` in `shared-poll.ts` applies the reply against the page's cursor by the rules a cursor poll applies (`classifyChange()`): it skips what changed before the page's position or what its cursor holds, and a takedown from before its position, and tells a new entry from an edit by when it was first published. PHPUnit checks the server's rules against `tests/fixtures/poll-cursor-cases.json` (`tests/test-shared-poll.php`, which CI runs); `tests/js/shared-poll-check.ts` checks the page's against the same file, as `npm test`, which CI also runs. With ads on, every entry in the reply first published at or after `since` carries a placement (`adHtml`, `adSlot`) and the reply carries `adsInterval`, since which entries are new depends on the page, and a page that applies the reply is at or after `since`; the page uses every `adsInterval`th placement among the entries new to it, counting on from its own `polledCount`. It keeps the later of its cursor and the reply's (`laterCursor()`), since a cached reply can be older than the page. When the page is behind the window, the window holds more than `POLL_CAP` changes, or a capped feed has a removal to apply, which only the server can backfill, the page sends its own cursor request instead, in the same poll (`fetchPollReply()`). Defining `NEWSPACK_ROLLING_COVERAGE_SHARED_POLLING` as false (the boolean, or the string `'false'` that `wp config set` writes without `--raw`), or the `newspack_rolling_coverage_shared_polling` filter returning either, turns it off (`is_shared_polling()`): pages render without `data-poll="shared"`, and shared replies carry `sharedPolling: false`, which moves open pages to cursor polling on their next poll. A shared request answered with a 400, or with a reply that isn't a shared reply (`isSharedReply()`), as a build without shared polling answers it, moves the page to cursor polling the same way, in the same poll. A body that can't be read counts too: the page can't tell a dropped connection from a server printing output ahead of its JSON, and its cursor keeps entries coming either way. On a page polling the shared URL, any other failure is a failed poll, and the next poll asks the shared URL again. A page that moved drops `data-poll` from its root and polls its cursor, and asks the shared URL again a minute later (`SHARED_POLL_RETRY_MS`), as does a page rendered without `data-poll`: after a quiet spell the CDN answers with its expired copy, however old, so the reply that moved the page can predate the site turning shared polling back on, as can a page cache copy of the page. A shared reply to a retry takes the page back to shared polling and restores `data-poll`; any other outcome, a failed request included, sets the next retry a minute on. The jump to the live feed takes the live block's `data-poll`, or its absence, with its cursor. Once a page sends credentials, it polls its cursor while it keeps `data-poll`. For a user who can edit posts, the login cookie makes the page cache and the CDN skip the request, so the shared reply would only cost the server its whole window, where a cursor poll costs one marker read while nothing changes. A page that takes credentials after a refusal (see `fetchEntries()`) gives up the shared reply from its next poll on, even where its requests could be cached.
- A cursor poll sends only what the page is missing. Its cursor (`Poll_Cursor`, `{ids}:{Y-m-d H:i:s}@{marker}`) holds the second of the newest change the page has, every entry it has as saved in that second, and the coverage's change marker (`rolling_coverage_change_marker` term meta, replaced on every change readers can see: a published entry saved, or an entry entering or leaving `publish`; draft saves leave it alone, so open pages keep their poll URL) from when the page took its copy. The entries list publishes a selection in parallel requests, so entries saved in one second become visible in any ID order; the cursor names them all rather than one. A render that opens at the newest entries takes the second from the coverage's newest change, read before its entries (`newest_change()`), unless the page shows a newer one: whatever changed up to then is on the page or where the feed lists it below the page, so an older draft published before the render isn't new to the page, and a bulk edit of entries it leaves out doesn't overflow its polls. A feed opened at a shared entry reads the newest change after its entries instead (`coverage_cursor()`), next to where it counts the newer entries, so only an entry published between those two reads can be counted on the page and again by the poll. A full or capped page's cursor also holds the entries from that second that load more lists after the page's bound (`listed_below()`, with load more's own query arguments from `load_more_args()`), which the page leaves out by design. It reads them right after the page's query, before the entries render, so an entry published while the page renders reaches it by poll; a page's cursor holds `PER_PAGE_MAX` entries at most, the room a poll makes for them. Edits made after the render to entries a page leaves out still come by poll, and the view script applies them when load more brings the entry in, since a cached load-more reply can predate them; an edit to an entry pinned by then shows it at once instead (see pinning below). One made before the render doesn't, so a load-more reply cached before it shows the entry as it was until that reply expires, and one cached before an older draft was published leaves that entry out until then. Edits to a new entry waiting behind the new-entries control come by poll as updates too, since the poll that brought the entry moved the cursor past it; the page keeps the latest (`offPageUpdates`) and applies it, with the entry's `data-arrival`, when the reader reveals the waiting entries (`takePendingEntries()`); an edit to an entry pinned by then takes it out of the queue and shows it at once instead. Load More is the only way a page reaches what it leaves out, so a change to what load more lists has to keep reaching all of it, which the load-more tests in `tests/test-same-second-entries.php` check. A cursor poll whose marker is still current answers without querying entries, including an empty marker before the coverage's first change; a cursor with no `@` queries once. One that queries leaves out the entries the cursor holds, which don't count toward `POLL_CAP`; it makes room for at most `PER_PAGE_MAX` of them, since the cursor comes from the request. On an uncapped feed, an entry saved again within the second the page holds it in arrives with its next save in a later second, and one taken down within that second can stay on the page until reload; a capped feed's whole-list reply after another removal or a burst brings either.
- The marker must change only after what a poll reads about the change is saved: a poll that takes the new marker without the change never looks for it again. `update_coverage_last_modified()` runs on `transition_post_status` after `Post_Type` records the publish and takedown times, and the page render and the poll read the marker before they read entries. Reading it first isn't enough where query results are cached: a request reads what invalidates them before it reads the marker (WordPress keeps the last-changed times from the request's first post query, which plugins often run while WordPress loads, and the Advanced Post Cache that WordPress.com and Atomic sites run reads its cache generation as it loads), so it could pair a new marker with entries cached before the change. Every entry query therefore carries the marker as a query var (`Poll_Cursor::MARKER_QUERY_VAR`, set in `coverage_entries_args()`), which `marker_where()` also writes into its SQL as a comment, so both caches keep a result per marker.
- A `staleTemplate` reply, to a poll or load more, reloads the page, whose fresh render stores the config again. A page cache can serve back the same copy, so `shouldReloadForStaleTemplate()` records each reload in session storage and reloads a page (path and query) again for the same coverage and key only once `OVERFLOW_RELOAD_RETRY_MS` has passed; without session storage it never reloads. A page that doesn't reload keeps polling, applying nothing and reporting failed checks, until the key is stored again or its next reload; its load more fails as a failed request does. Unlike an overflow, this reloads a capped feed's host page and a shared-entry view too, since nothing else gets their entries in the right template. A feed that shows no entries ignores the reply.
- A page drops the entries a poll names as taken down and leaves them out of later polls and load more until reload, so a restored entry returns only with a fresh render. An entry with no recorded publish time, such as one created straight into `publish` (core REST, WP-CLI, or source ingestion with auto-publish on), gets one only when it is published again (`record_entry_published_gmt()`). Taken down and published again between two polls, it is back in `publish` when the second runs, so that poll sends it as new instead of naming it. A page that shows it replaces it in place; one holding it behind the new-entries control swaps in the new copy where it waits, with the waiting entry's ad, so the control counts it once. A capped feed can't load an entry to fill the gap: after a removal, its poll brings the removals and up to twice its count of newest entries with `replace`, and the page swaps its list. A burst past `POLL_CAP` gets the same reply, in place of the overflow that reloads an uncapped page.
- Pinning or unpinning saves the entry again (`Post_Type::handle_toggle_pin()`), so the next poll brings it: as an edit, or as a new entry when it was published since the page's last poll. A fresh render lists pinned entries first, in the order they were pinned (`Post_Type::orderby_pinned_first()`), so a page puts a pinned entry it adds below the pinned entries it shows: an edit, whether it showed the entry before or not (`showPinnedEntry()`); a new entry, ahead of the unpinned ones that arrive with it or after it; and one load more brings pinned at its date, once a poll sends it, as a load-more reply can come from a cache older than an unpin. Load more then skips it as already shown. In a shared view, a pinned entry is out of the count of newer entries, as a fresh render leaves pinned entries out of it, whether the render or a poll counted it (the page goes by each entry's `data-date-gmt`), and back in it once unpinned; past a hundred, the rendered count is the server's cap and stays as it is. Known limits, until reload: pinned entries a page adds land after the ones it shows, so entries pinned within one poll interval, or one pinned before it went live after others were pinned since, sit out of pin order; and the count can be one off for a pinned entry taken down before the render and restored since, or re-dated across the shared entry since, as the page goes by the date the entry has now. A capped feed ignores pinning.
- A page that shows a newly unpinned entry moves it to where a fresh page lists it: above the first unpinned entry dated before it, by the GMT date each entry carries (`data-date-gmt`, the date load more pages by), then by ID. Past the last unpinned entry shown, it goes last, unless load more's bound (`before`) lists it below: then it leaves the page until load more brings it, unpinned even from a reply cached before the unpin (`offPageUpdates`). The bound sits lower than the last entry shown after a page of older entries that ended on a pinned entry. A feed with `olderEntries` set to `none` has `hasMore` false, so the entry goes last there even when the bound lists it below: the page can't tell such a feed that leaves entries out from one that shows them all. A feed opened at a shared entry counts an unpinned entry dated in a later second than the shared one among the newer entries instead, as a fresh page would.
- Each poll response carries the coverage's `status` and `newestEntry`. The view script dispatches `newspack-rolling-coverage:poll` on `document` with both (`src/blocks/shared/poll-event.ts`); the Coverage Status block listens for it. A feed with `hideWhenEnded` removes itself when a poll reports `archived`; any other feed shows its ended notice, as a fresh render would. On a page whose coverage hasn't ended, the notice exists only as data on the wrapper (`ended_notice_data()`): `data-ended-notice` (its text), `data-ended-notice-link` (the link's text, when the notice links) and `data-ended-notice-url` (the block's own URL, when it sets one). Rendered as markup, even hidden, the text would show wherever the page is read without its script or with attributes dropped, such as a syndication feed, an email or a copy cleaned to text. `showEndedNotice()` in `view.ts` builds the notice first in the Feed and announces it. Without a URL of its own, the link goes to the coverage's latest breakout post, which may only be published at the end, so once the coverage has ended each poll response carries it as `latestBreakoutUrl` (null without one). The view script links only an http or https URL, from either source, since an author without `unfiltered_html` can write a feed wrapper's data attributes.
- Each time the feed schedules a check, starts one, or stops checking, it writes `data-check-state` (`waiting`, `checking` or `idle`) on its root, with `data-next-check-at` (milliseconds) while waiting, and fires `newspack-rolling-coverage:check` on `document` (`src/blocks/shared/check-event.ts`). The first report after a check carries its result: how many new entries arrived, shown or waiting behind the new-entries control, or that it failed. No result is carried for an overflow reply or for a feed that shows no entries, which can't count arrivals; a `staleTemplate` reply that doesn't reload the page reports a failed check. A feed that checks only on request, whose coverage isn't live, that is hidden in a background tab, or that has stopped reports `idle`. The [Update Timer](../update-timer/DEVELOPMENT.md) block follows it; the root attributes let a timer whose script runs after the feed's first report pick up the current state.
- Older entries follow the `olderEntries` attribute (`scroll`, `button` or `none`; `Rolling_Coverage_Block::older_entries()` treats an unknown value as `scroll` and a capped feed as `none`). `scroll` renders the `.newspack-rolling-coverage-sentinel`, watched by an `IntersectionObserver`. `button` renders a `.newspack-rolling-coverage-load-more` wrapper holding a core-styled button after the entries. `none` renders neither and sets `data-has-more="0"`. The view script reads the mode from the markup, and both triggers call `loadMore()`, which requests entries `before` the last one loaded. The bound is `{id}:{post_date_gmt}` (`load_more_bound()`), and every feed query lists entries by date, then ID (`FEED_ORDER`), so entries published in the second of the last one loaded continue below it rather than being skipped. A page showing only pinned entries lists them in pin order, so its last entry's date would skip any entry dated after it. Its bound is a bare date a minute past the render instead (`load_more_top_bound()`), above every published entry since WordPress schedules a post dated a minute or more ahead, and load more lists every entry from the top; the view script skips the pinned entries the page already shows, as it skips any entry it already has or holds behind the new-entries control, along with an ad that follows one.
- The button's wrapper is rendered `hidden` and the view script reveals it while `hasMore` is true, so it never shows as a dead control before the script runs or without it. While a page loads it carries `aria-busy` and `aria-disabled` rather than `disabled`, which would drop focus. After a load, focus moves to the first new entry; a failed load is announced and leaves the button in place to retry.
- `hasMore` comes from fetching one entry more than a page (the page render, the REST `before` page and the editor preview), so a coverage whose entry count is an exact multiple of the page size shows no button on its last page.
- The feed's REST URL comes from the block's markup, which an author without `unfiltered_html` can still set, and with it the server whose HTML the feed inserts. So `initBlock()` honours `data-rest-url` only when it is same-origin with the page (`isSameOrigin()`), and `fetchEntries()` drops a reply that a redirect carried to another origin or that isn't JSON, like an uploaded text file; the jump to the live feed likewise takes only an HTML page from this origin. A page served from a host other than `rest_url()`'s, such as an alias domain nothing redirects, therefore stays a static first page and logs a console warning, even though WordPress's REST CORS headers would let it poll cross-origin. Every fragment a feed inserts — entries and ad markup alike, from a poll, load more or the jump — also passes through `sanitizeHtml()`, on top of the server's KSES. It drops scripts, `object`/`embed`, `base`, `meta[http-equiv]`, SVG `animate`/`set`, `on*` handlers and `srcdoc`, `javascript:` and `vbscript:` URLs in any attribute, and `data:` URLs in `href`, `src`, `xlink:href`, `action` and `formaction`. A provider's ad placeholder survives it; the ad's own script loads the creative later. The jump also copies the live page's stylesheets, which carry CSS only.

The "Jump to Latest" control is not part of any layout. `render_new_entries_control()` renders it for every uncapped feed, inside the Feed after the header blocks, except in a syndication feed or inside an entry's content:

- It is a `core/buttons` block holding one `core/button` (`latest_buttons_block()`), styled by the theme's button styles plus the Elevation 2 shadow (`style.scss` defines it for themes without the preset), with no palette colors. Its link goes to `live_feed_url()` and carries `data-rc-latest` (`LATEST_ATTRIBUTE`); its wrapper carries the class `newspack-rolling-coverage-new-entries` and `data-live-url`, which `view.ts` looks for. `style.scss` fixes it to the top of the viewport.
- In the normal view it renders `hidden`, and `view.ts` shows it with the count of new entries. In a shared-entry view it shows with `data-newer-count`; when there are newer entries, the link reads `newer_entries_label()` and keeps its own text in `data-label`. An unpinned new entry from a poll joins that count only when it is dated in a later second than the shared entry, as `count_newer_entries()` counts. An older one, such as an entry taken down and published again between two polls, goes to its place by date as an unpinned entry does, and when that is below load more's bound, load more shows it with the poll's copy.
- Its text is the site-wide label from `Latest_Label` (`includes/blocks/class-latest-label.php`): the `rolling_coverage_latest_label` option, or "Jump to Latest" when it's empty. `GET` and `POST rolling-coverage/v1/settings/latest-label` read and save it as `{ "label": "" }` for users with `edit_others_posts`, like the status labels. The label is plain text, capped at 40 characters (`MAX_LENGTH`); posting an empty string deletes the option, and omitting `label` leaves it unchanged. The plugin's settings screen (`src/admin/components/settings-modal.tsx`) uses it.

What readers see entries called comes from `Entry_Name` (`includes/blocks/class-entry-name.php`): the `rolling_coverage_entry_name` option, `{ "singular": "", "plural": "" }`, each word as it reads mid-sentence. `GET` and `POST rolling-coverage/v1/settings/entry-name` read and save it with the same permission as the status labels. Each word is plain text capped at 30 characters (`MAX_LENGTH`); both empty deletes the option, one without the other, or a request with only one of them, returns a 400 (`rolling_coverage_entry_name_incomplete`), and a stored name missing a word counts as none. Every reader-facing string that names entries has two forms: its own translated wording, used when the site sets no name, and a translatable template (`No %s yet.`, `%1$d New %2$s`) filled with `Entry_Name::word()` in sentences or `Entry_Name::title_word()` in button labels, which capitalizes each all-lowercase word only where the locale starts with `en`. The word follows `count === 1`, not the locale's plural rules, and its grammatical gender is unknown to translators: the price of a two-word setting. The PHP strings are the empty feed (`no_entries_text()`), the shared-entry count (`newer_entries_label()`), the archived entry notice (`archived_entry_notice_text()`, before the `newspack_rolling_coverage_entry_archived_notice` filter) and the Share block's `aria-label`. The layout's all-updates link (`See all entries` / `See all %s`) is set in the editor and fixed when the layout is created, not at render. The view script's strings live in `entry-name.ts` and read the name from the wrapper's `data-entry-name` (`Entry_Name::for_script()`), present only when the site sets one; the jump to the live feed copies it from the live page with the cursor. Like the other site-wide labels, a change reaches cached pages only as their cache expires.

Entry bindings use the `newspack-rolling-coverage/entry` source, registered by `Entry_Bindings::register_source()`. Keys: `breakoutUrl`, `breakoutLabel` and `shareUrl` resolve per entry; `coverageName` and `followTag` resolve per coverage. `breakoutLabel` is the label of the entry's published breakout post, and null without one, which drops a bound paragraph (see Breakout cards). The editor registers the same source in `src/blocks/shared/entry-bindings.ts`; it resolves only `coverageName` and `breakoutLabel` (the site-wide label) and leaves the rest empty. `Entry_Bindings::filter_button()` drops a bound button whose value is empty and adds the data attributes the view scripts need.

## Lite Site pages

The Lite Site plugin serves cached, text-only copies of posts. It renders a post's blocks inside its `newspack_lite_site_post_content` filter, strips scripts and every attribute outside a short allowlist, and prints no enqueued assets. `Lite_Feed` (`includes/blocks/class-lite-feed.php`) keeps a feed live there with the same view script:

- **Detection.** A block that renders while that filter runs is rendering for a lite page (`Lite_Feed::is_lite_render()`). There `render_block()` renders each entry as text through `Lite_Feed::render_entry()` rather than the entry template, skips `render_feed()`, ads and the Follow button, and marks the wrapper `data-lite="1"`. Coverage Status leaves out its "Updated" line, and its badge shows the status the page rendered with.
- **Markup and assets.** Once a feed renders, `Lite_Feed::allow_feed_markup()` widens Lite Site's allowlist through `newspack_lite_site_allowed_html` to keep what the view script reads. Only then do the feed's few styles and its view script print, through Lite Site's `newspack_lite_site_styles` and `newspack_lite_site_single_after_footer` hooks. A Lite Site without that filter keeps a plain lite feed, with the Load More and Check for Updates controls hidden, since nothing would run them.
- **Polls and load more.** `view.ts` sends `lite=1` from a lite wrapper, and the entries route then renders `Lite_Feed::render_entry()` too, so a polled entry matches the page.
- **Caching.** Lite Site caches each page by its path for every reader, so lite output can't depend on the reader or the query string. `render_block()` renders a lite feed for a signed-out reader, as its polls and load more are, so blocks that render by reader, in the layout or in an entry, come out as a signed-out reader gets them. The feed also opens at the newest entries with no shared-entry view, prints no per-reader data, judges password protection by `post_password` rather than the reader's cookie, leaves out blocks Newspack shows only to signed-in readers (`Entry_Bindings::public_content()`), shows a gated entry's teaser (see Server rendering and polling), and links the live feed by its bare path (`live_feed_url()`).

## Styling policy

A layout's look comes from block settings in its template: colors, typography, spacing and borders, using theme presets with fallbacks. Publishers can then change them in the editor, and the pattern carries them to every synced block. A color names the block theme's palette preset first, then the classic Newspack Theme's custom property, then, where one is safe, a plain value, as in `var(--wp--preset--color--base-2, var(--newspack-theme-color-bg-light, #f7f7f7))`. It then follows the theme's style variations, dark ones included; a fixed step like `--wp--custom--color--neutral-5` doesn't change between variations. Keep the plugin's CSS structural:

- `style.scss` (built to `view.css`, loaded on the front end and in the editor) holds structural rules only. Rules that size items use `:where()` so block settings win.
- `editor.scss` covers editor-only UI.

Don't add a layout's colors or type to these files.

The Full Story Entry's box follows the policy: its border (in `READABLE_ACCENT`; Bulletin's and Minute's have none), radius, padding, Block spacing and background are block attributes, so publishers can restyle the card. `style.scss` holds only its behavior: the `--newspack-rolling-coverage-accent-tint` custom property, defined on `:root` as 5% of the accent; a `scale(1.01)` on the hover of a box without a button (200ms `ease` transform transition, only under `(hover: hover) and (pointer: fine)` and `prefers-reduced-motion: no-preference`, since touch fires hover on tap and the scale is decoration); the title's link stretched over the box with an `::after`, except in a box holding a button; `z-index` for every other link and button in the box; and the focus ring when the title's link takes keyboard focus. The background is a custom property because the block's `style` attribute is filtered by KSES and `safecss_filter_attr()`, which strip `color-mix()` but let `var()` through. The layouts' `color.background` is `var(--newspack-rolling-coverage-accent-tint)`, except Bulletin's and Minute's `PINNED_BACKGROUND`; a publisher who picks another color replaces it.

The one exception is a ruled Feed: a Feed group with the class `newspack-rolling-coverage-ruled` (`RULED_FEED_CLASS`, used by Ticker) gets a 1px rule centered in every gap between its items, in a color mixed from the text color. Borders can't do this: a border sits inside its cell, so the cells' text widths differ and the rule can't sit in the middle of the gap. Publishers can't restyle the rule, but its space follows the Feed's Block spacing: `style.scss` doubles the row and column gaps and adds 1px, so a rule has a full gap on each side. Each item's `::before` draws the rules above it and on its inline-start side (left, or right in RTL, set with `:dir()` so it holds whether WordPress serves `view.css` or `view-rtl.css`), and the Feed clips its content box so the ones that would land on its outer edges disappear; the CSS needs no column count or breakpoints. The gaps reach the stylesheet as `--newspack-rolling-coverage-gap` and `--newspack-rolling-coverage-column-gap` (`feed_gap_declaration()`, `feedGapStyle()`); it derives `--newspack-rolling-coverage-rule-row` and `--newspack-rolling-coverage-rule-column` from them, registered as lengths so they compute once on the Feed. A synced preview leaves the gap of a ruled Feed to the stylesheet (`feedPreviewProps()`).

A ruled Feed with a horizontal flex layout is a ruled row (Ticker): the entries element (`.newspack-rolling-coverage-entries`) turns into a single line that scrolls sideways, the items before it take a fixed 12rem column beside it, and the items after it take a line of their own; the row always wraps, whatever the Feed's "Allow to wrap" setting. Up to three entries share the line's width, down to 8rem each, so they only scroll in the narrowest spaces; four or more keep a 12rem minimum and scroll once they don't fit. A row draws no rules on its outer edges, so it doesn't clip and keeps its background, border and padding: the items before the entries draw none, the items after draw only the rule above them, and the entries element draws the rule between it and the header as its own inline-start border, clipping the rules its entries draw on its edges as a scroll container does. Once the Feed is narrower than 48rem (a container query on the Feed, not a viewport breakpoint) the header and the entries each take a full line and that border moves above the entries. Where the browser supports scroll-driven animations, a mask fades the entries out at any edge with more to scroll, so the fade shows the Feed's own background, the page's or an image's alike; elsewhere, Firefox included, the line is cut at the edge. Snapped entries line up with the line's own padding (`scroll-padding-inline` of one rule gap, none at the start once stacked), widened to the fade where it shows, so snapping and scrolling a focused headline into view keep clear of it; on keyboard focus, `view.ts` scrolls the focused headline's entry fully into view, since Chrome leaves a link that already partly shows where it is, and scrolling the entry rather than the link lands on a snap position. The scroll container clips anything past its edges, so focus rings inside the line sit just inside their links (`outline-offset: -2px`). The editor matches the site: `entry-previews.tsx` wraps an editable row's entry and its previews in the same entries element (`isRuledRow()`), and a synced preview always has one. A row only makes sense capped: picking Ticker caps the block, and the block hides its Show setting while it's capped. A custom layout with a ruled row picked on an uncapped block stays uncapped until Show is set to Latest, and until then the editor shows a pinned card beside the header and older pages load sideways. Known limits of a ruled row: the Feed is a size container, so inside a parent that sizes it to its content (a Row group, say) it collapses; a tablet or mobile orientation override on the Feed isn't supported; and, as for a ruled grid, tablet and mobile Block spacing don't apply to its gaps. Known limits of a ruled grid: the clip also trims the Feed's own background, border and padding, so give a wrapper group those styles instead; it leaves no room on the inline-start edge, so a focus outline there is cut on that side, and a linked entry's outline, which reaches further out than the clip allows, is cut on every outer edge; an uncapped Feed with the fixed "Jump to Latest" control clips with `overflow` instead, which fixed children escape, keeps no room on any edge and clips at the padding box, so Feed padding shows the edge rules; tablet and mobile Block spacing don't apply to a ruled Feed's gaps, and a percentage gap collapses to 1px; and a minimum column width, sized by core for the undoubled gap, fits one column fewer.

## Motion

Entry text never slides or shifts: entries and notices only fade, the new-entries control drops in slightly, pressed buttons scale a little, and a full story box without a button grows slightly on hover (see Styling policy). All of that motion is off under `prefers-reduced-motion: reduce`, in `style.scss` and, where script adds a class, in `view.ts` (`MOTION_QUERY`).

- `fadeIn()` adds a class to elements the script inserted and removes it on the element's own `animationend`, or after `FADE_CLEANUP_MS` if the animation never runs. `is-entering` fades in from transparent over 200ms on every entry `insertNewEntries()` adds and on entries load more appends, and over 250ms on the ended notice. An entry replaced in place by an edit gets `is-updated`, which fades it up from half opacity over 150ms so the text a reader is on doesn't blank out; an edit that pins or unpins the entry fades it as it moves. Server-rendered content doesn't fade.
- The new-entries control pops in over 250ms (`newspack-rolling-coverage-pop-in`), fades out over 120ms (`is-leaving`, `hideNewEntriesControl()`) and gets `hidden` after `NEW_ENTRIES_FADE_MS`; showing it again cancels the pending hide (`cancelNewEntriesHide()`).
- Load More and Check for Updates buttons dim to `opacity: 0.7` while `aria-busy="true"`. A state change rather than motion, it applies under reduced motion too, and it sets no transition, so the theme's button transitions stay as they are.
- Inside a feed, Share buttons and the Follow button scale to 0.97 while pressed, where the device hovers with a fine pointer. The transition is set on `:active` only, since a `transition` on the button would replace the theme's hover transitions; the press eases in, and the release follows the theme's own transition, snapping back where the theme sets none. Share as a text link doesn't scale, and neither does a Follow Coverage block outside a feed.

## Gotchas

- **Wide layouts set the Feed's width too.** Ticker and Split set the block's `align` to `wide` when picked, and their Feed group is `align: wide` as well. While a layout is shared the editor draws it as a preview, but a detached layout renders its Feed as a real nested block, and the classic Newspack Theme's editor caps a block without an alignment at the content width, so without its own alignment the Feed shrank inside the wide block. The inner blocks layout (`INNER_BLOCKS_LAYOUT`) offers `wide` as well as `full` for this. On the front end a nested `alignwide` changes nothing on block themes. The classic theme gives any `.alignwide` inside the content breakout margins on its wide templates (and in its header and footer widget areas), so `style.scss` resets a wide or full group directly inside a block that isn't full width, as it already did for full; the Feed then follows the block's own alignment, whatever it is set to. The same templates center and cap the grandchildren of a `.wp-block-group.alignwide` (`> div > *`), which would shrink the Feed's entries in their grid cells, or center Flash's entry inside its bar, so `style.scss` resets those for a wide Feed anywhere in the block, under `.wp-theme-newspack-theme` (the classic theme and its style variations, which are its child themes) so block themes don't load a rule they don't need. Inside a full-width block the theme's own nested-wide centering applies.
- **Stored patterns are not reconciled.** Once a built-in layout's pattern exists, changes to `layout.ts` or `template.ts` do not reach it or the blocks synced to it; `create_layout()` returns the existing pattern. To try a changed template, trash the pattern, reload the editor and pick the layout again, which creates a new one. Blocks still pointing at the trashed pattern render the built-in Bulletin layout until they pick a layout again.
- **Synced previews rebuild the Feed's wrappers.** A shared layout's Feed and the groups around it are drawn as plain containers (`FeedWrappersPreview`, `feedPreviewProps()`), not real blocks, so core's elements support never sees them. Each coverage-level block previews in its own container (`chromePreviewStyle()` sizes it), since the site renders each as its own Feed item; a row like Alert's would otherwise stack inside one container. `groupElementsCSS()` prints the link and heading colors a wrapper sets (Flash's bar, for one) as a `<style>` scoped to that container. Like the rest of the synced preview it shows the desktop layout, without the Feed's tablet and mobile overrides. With a classic theme, a detached Feed inside a group keeps its alignment wrapper (`.wp-block[data-align]`) and the 28px block margins core's classic editor styles give it, so `editor.scss` resets them.
- **Capped feeds are previews.** A block with `latestOnly` ignores pinning (`$is_pinned` is false, and the query sets `Post_Type::SKIP_PIN_ORDER_VAR`). It also shows no ads, loads no older entries, and has no new-entries control or live region. It never makes a page the coverage's page or a live blog: `Page_Coverages::collect_feeds()`, `Schema::get_coverage_blocks()` (no `LiveBlogPosting`) and `Placements::page_id()` all skip it. It still counts as a place that shows the coverage, listed with its layout and how many entries it shows (see "Placements" in `src/admin/DEVELOPMENT.md`).
- **Editable layouts preview the other entries inside the Feed.** A detached layout, or a layout pattern being edited, shows its entry template as editable blocks, previewed against up to three entries (the pinned one, a regular one and one with a breakout post), and every other entry as a static preview. `entry-previews.tsx` renders them right after the Feed's last per-entry block, where the site renders the entries, skipping blocks that Block Visibility hides in any viewport (core doesn't render a hidden block, filters included), so a grid Feed places them in its cells and a footer stays below them. Anything rendered after the Rolling Coverage block's inner blocks lands outside the Feed instead. The previews sit inside the editable layout, so they render copies of its blocks with the same client IDs and inherit its React context: `EntryPreviews` resets the anchor and pinned entry contexts around them, and the CSS that hides blocks in the editable entry skips them.
- **Placeholders wait for their data.** The editor shows `LoadingState` until the preview has what its blocks read, so core blocks don't flash their own placeholders. After `fetchEntryPreviewContexts()`, the entries effect resolves each entry with `getEntityRecord()` and then each unique author with `getUser( id )` (what core's Post Author Name and Avatar blocks read) and `getUser( id, { context: 'view' } )` (what Post Author reads), so those blocks find the user already loaded. Users without `list_users` (Authors, Contributors) can't read another user in the default context, so for them those two blocks still show core's placeholder. The sample entries (`samples.ts`) receive their authors for the `view` context and mark both `getUser` resolutions finished for the same reason. The coverage combobox (`renderCoverageCombobox()` in `edit.tsx`, and `CoveragePicker` in `shared/`) shows `LoadingState` until the first, empty-search request resolves, so it never reads "No items found" before the coverages arrive; the sidebar's copy stays silent while the placeholder shows its own, so it's announced once. Later searches are debounced and use the combobox's own `isLoading`.
- **Entry times use the site's time zone in the editor.** Core's `core/post-data` binding gives Post Date the entry's local `date` or `modified`, which have no offset, and Post Date formats them with `dateI18n()`, which reads a string without an offset as browser time. An editor whose browser zone differs from the site's (a UTC site viewed from London in summer, say) saw formatted times shifted; relative times (`human-diff`, as in pinned cards) were already right. `entry-date-preview.tsx` filters `editor.BlockEdit` for a Post Date on an entry bound to `core/post-data` and passes `getDate( datetime )`, the same local time read in the site's zone. It applies wherever an entry is the Post Date's context: the Rolling Coverage preview, and the entry's own editor. A value with an offset is left alone, so a core fix won't be applied twice. The front end was never affected.
- **Per-viewport styles.** WordPress 7.1 stores tablet and mobile overrides under `style['@tablet']` and `style['@mobile']`, with breakpoints from `WP_Theme_JSON::get_viewport_media_queries()`. The Split template uses them for grid columns and spans. A horizontal Feed can use them to become a column on tablets or phones. Because core changes only the direction, not the `is-horizontal` class, `style.scss` sizes a horizontal Feed's entries with `flex: 1 1 0`, a minimum width and `width: 100%` rather than a 24rem flex basis, which would become a 24rem height in a column; the width fills the column and is ignored in a row. Core prints layout styles and Block Visibility styles only for blocks rendered on the page, so the block stores the template's styles up front (`store_template_layout_styles()`, `store_grid_placement_styles()`) for entries that arrive later by polling or scroll. Check polled entries when a layout depends on these overrides.
- **One-line rows.** A horizontal Feed set to not wrap (`flexWrap: nowrap`, core's `is-nowrap` class) keeps its items side by side at every width, as Flash does. `style.scss` lets the entries shrink to whatever room the other items leave (`min-width: 0` instead of the 24rem minimum that makes a wrapping Feed wrap); the other items keep their width unless they don't fit on their own, and then wrap. An entry group set to not wrap, inside a horizontal Feed, does the same for its excerpt, which then shows one line ending in an ellipsis instead of the line clamp, unless it has an inline read-more link, which the ellipsis would hide. The Feed's entries wrapper (`newspack-rolling-coverage-entries`) lays its entries side by side on one line and clips the overflow (`overflow: clip`, since `hidden` would let `scrollIntoView` or an `#…-entry-N` link scroll the wrapper sideways onto hidden entries; ruled rows such as Ticker are excluded): one entry takes the whole wrapper, two take half each, three or more take a third each, with the Feed's gap counted in the widths so the fourth and later entries sit fully past the edge. The count comes from `:has(> :nth-child())` setting `--nrc-visible-entries`, so entries arriving or dropping by polling resize the row with no script. Entries past the visible ones are `visibility: hidden`, which also takes them out of the tab order and the accessibility tree. On phones (782px and below) only the first entry shows. Flash's time is hidden on small phones (core's mobile breakpoint, 480px and below) with core's Block Visibility (`metadata.blockVisibility.viewport.mobile`), so a publisher can show it again from the block's settings. The synced preview's wrappers carry `is-nowrap` too (`groupPreviewParts()`) and use the same entries wrapper, so the rules above apply to the preview unchanged. An editable (detached) layout wraps its entry previews in the same wrapper for such a Feed (`isOneLineRow()` in `edit.tsx`). Alert's coverage name (`newspack-rolling-coverage-name`) fills the room left and keeps to one line, ending in an ellipsis. The all-updates link in such a row doesn't shrink and keeps to one line up to half the row's width, wrapping beyond that, so the name gives way first and a long or translated link can't overflow. The editor's synced preview wraps each coverage-level block in its own container, so `editor.scss` repeats both rules one level down.

## Tests

PHP tests live in `tests/`; `test-layout.php` covers layout creation and lookup, `test-shared-entry-view.php` covers the "Jump to Latest" control, `test-latest-label.php` covers its label option and REST route, `test-breakout-card.php` covers the breakout summaries, the compact layouts' filters and their Full story label, `test-full-story-entry.php` covers the Full Story Entry (selection, rendering, featured image, label, grid placement, column rules and polls), `test-breakout-label.php` covers that label's option and REST route and a post's own label, `test-entry-name.php` covers the entry name option, its REST route and the labels that use it, and the per-layout `test-ticker.php`, `test-split.php` and `test-byline.php` show how to test a layout that relies on server behavior.

When the plugin is checked out under newspack-workspace's `repos/plugins/`, run them from the plugin directory with `../../../n test-php` (add `--filter` or `--group` to narrow). The tests register the blocks from `dist/`, so build first if it is stale. Outside the workspace, `npm run test:php` runs `./vendor/bin/phpunit` against the WordPress test library, which `bin/install-wp-tests.sh <db-name> <db-user> <db-pass> [db-host] [wp-version]` installs; `tests/bootstrap.php` reads it from `WP_TESTS_DIR`, or `/tmp/wordpress-tests-lib` by default. `npm test` runs `tests/js/shared-poll-check.ts`, which checks the page's side of shared polling, including its copy of the cursor rules against `tests/fixtures/poll-cursor-cases.json` (see Shared polling); CI runs it too. Run `npm run typecheck` and `npm run lint:js` for the rest of the TypeScript side.
